# APP-102 | Containerizing a Production Next.js Application

**Date:** Day 2  
**Ticket:** APP-102  
**Scope:** Multistage Docker build for a Next.js application targeting minimal, production-ready image size  
**Outcome:** Image built successfully at 243MB uncompressed / 59.6MB compressed. Container runs and serves on port 3000.

---

## Objective

Containerize the `sample-next-app` using a production-grade multistage Dockerfile. The image must be deployable to a local k3d cluster via a private registry, with image size optimized for real-world registry push/pull performance.

---

## Technical Decisions & Rationale

### 1. Output Mode: Standalone

Next.js supports three output modes — server (default), static export, and standalone. The standalone mode was selected for the following reasons:

- Produces a self-contained `server.js` with only the Node.js modules the application actually uses, determined statically at build time
- Eliminates the need to ship the full `node_modules` tree in the production image, reducing image size by ~75–80%
- The resulting artifact is a single runnable folder, making it the most container-friendly output mode

**Config change required in `next.config.js`:**
```js
const nextConfig = {
  output: 'standalone',
}
```

Without this, `npm run build` does not produce `.next/standalone/` — the COPY instruction in the production stage would fail silently or throw a path error.

### 2. Base Image Selection

Both stages use `node:20-alpine`. Alpine was selected over the default `node:20` for its significantly smaller footprint (~50MB vs ~1GB). Since this application has no native npm dependencies that require `glibc`, Alpine's `musl` libc is not a compatibility concern here.

**Decision rule for future reference:**
```
Try alpine first → if native module breaks → fall back to node:slim
```

### 3. Layer Caching Strategy

Dependency installation (`npm ci`) is expensive. Source code changes frequently; `package.json` does not. Structuring the COPY instructions to separate these two concerns ensures Docker's layer cache serves the expensive step on most rebuilds:

```dockerfile
COPY package*.json ./   # rarely changes — layer gets cached
RUN npm ci              # only reruns when package.json changes
COPY . .                # changes on every commit — runs last
```

Inverting this order would invalidate the `npm ci` cache on every code change, adding 30–90 seconds to every build unnecessarily.

## Implementation

### Dockerfile

```dockerfile
# Build Stage
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Production Stage
FROM node:20-alpine AS production
WORKDIR /app

COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public

EXPOSE 3000
CMD ["node", "server.js"]
```

### Why Three Separate COPY Instructions in Production Stage

Next.js standalone output intentionally excludes static assets to keep the core artifact minimal. The three COPY lines wire together three separate pieces:

| Artifact | Source | Purpose |
|---|---|---|
| `.next/standalone` | Generated by build | Server runtime — contains `server.js` and minimal deps |
| `.next/static` | Generated by build | Browser assets — JS chunks, CSS, fonts |
| `public/` | Developer-authored | Static files served directly — favicon, images, robots.txt |

Omitting `.next/static` results in a running server that returns blank pages — the HTML shell loads but all JS and CSS 404. Omitting `public/` results in 404s on all static asset routes.

### .dockerignore

```
node_modules
.next
.git
.gitignore
README.md
.env
.env.*
```

`node_modules` exclusion is critical — without it, `COPY . .` would bring the local `node_modules` into the build context, potentially overriding what `npm ci` installed inside the container and introducing platform-specific binary mismatches (local machine vs Alpine Linux).

## Issues Encountered

### Issue 1 — Container Exiting Immediately After Start

**Symptom:** Container started and stopped within seconds. No obvious error.

**Investigation:**
```bash
docker logs <container_id>
```

**Output:**
```
▲ Next.js 16.2.10
- Local:    http://<container_id>:3000
- Network:  http://<container_id>:3000
✓ Ready in 0ms
```

**Root Cause:** The application was healthy. The container appeared to stop because it was run without the `-p` port mapping flag, so there was no bound port to keep the session observable. The container was actually still running — it was not exited.

**Resolution:**
```bash
docker run -p 3000:3000 my-nextjs-app
```

**Learning:** A container running a long-lived process (HTTP server) does not exit on its own. If it appears to exit, first check logs before assuming a crash. Absence of a port mapping does not stop the container — it just makes the service unreachable from the host.

## Key Concepts Documented

**WORKDIR behavior:** `WORKDIR /app` creates the directory if it does not exist. It has no dependency on the local filesystem structure — it is a Docker-internal instruction equivalent to `mkdir -p /app && cd /app`.

**Multistage isolation:** Each `FROM` statement starts a completely independent filesystem. The production stage `/app` starts empty. Only explicitly `COPY --from=builder` instructions transfer content between stages. All other build-stage content — `node_modules`, source files, build cache — is discarded permanently.

**Build-time vs runtime environment variables:** Variables prefixed `NEXT_PUBLIC_*` are inlined into the JavaScript bundle during `npm run build`. They are resolved at build time, not at `docker run` time. Passing them as `-e` flags at runtime has no effect — the bundle already has the values compiled in. Non-public variables (e.g., `DATABASE_URL`) are safe to inject at runtime.

**EXPOSE is documentation only:** `EXPOSE 3000` does not open or bind any port. It signals intent to operators and tools. Actual port binding happens at `docker run -p 3000:3000`.
